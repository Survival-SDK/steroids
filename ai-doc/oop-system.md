# OOP-система движка Steroids

## Базовые классы

### st_object_t - базовый класс для всех объектов

Определен в `include/steroids/object.h`:
- Содержит `funcs` (указатель на таблицу виртуальных функций). **Важно:** При создании объекта дочернего класса это поле подменяется на таблицу функций дочернего класса.
- Содержит `owner` (указатель на владельца объекта)
- Имеет метод `destroy()` (деструктор)

### st_modctx_t - базовый класс для контекстов модулей

Определен в `include/steroids/modctx.h`:
- Наследуется от `st_object_t` через безымянный член
- Представляет контекст модуля (singleton или обычный экземпляр)
- Используется для хранения зависимостей и состояния модуля

## Создание объектов

### Создание контекста модуля

```c
st_xxxctx_t *ctx = (st_xxxctx_t *)st_modctx_new(
    "subsystem",           // Имя подсистемы
    "name",               // Имя реализации
    sizeof(st_xxxctx_t),  // Размер структуры
    NULL,                 // Владелец контекста (owner, пока всегда NULL)
    &xxxctx_funcs,        // Таблица функций
    (st_object_dtor_t)st_xxx_quit  // Деструктор
);
```

**Примечание:** 4-й параметр (`owner`) в данный момент для всех контекстов выставляем на `NULL`. Позже этот параметр будет либо удален, либо как-то использован.

### Создание обычного объекта

```c
st_xxx_t *obj = (st_xxx_t *)st_object_new(
    "subsystem",
    "name",
    sizeof(st_xxx_t),
    owner_ctx,            // Владелец объекта (контекст, создавший объект)
    &xxx_funcs,
    (st_object_dtor_t)st_xxx_destroy
);
```

## Наследование

Используем безымянные структуры (требует `-fms-extensions`):

```c
// Родительский класс
typedef struct {
    st_object_t;
} st_parent_t;

// Дочерний класс
typedef struct {
    st_parent_t;  // Наследование - все поля parent доступны напрямую
    int child_field;
} st_child_t;
```

Доступ к полям родителя:
```c
st_child_t *child = ...;
// child->funcs доступно, но значение подменено на таблицу дочернего класса
```

**Важное правило:** Доступ к полям родительского класса следует производить **только через геттеры** (если они есть) или через другие инструменты (макросы, прямой вызов функции в обход таблицы функций). Не обращайся к полям родителя напрямую из кода дочернего класса. Хотя C не поддерживает `protected`-поля как C++, старайся следовать этому принципу инкапсуляции.

## Таблицы функций

### Для контекстов модулей

```c
static st_xxxctx_funcs_t xxxctx_funcs = {
    st_modctx_funcs,  // Наследуем функции от st_modctx_t
    .custom_func = st_xxx_custom_func,
};
```

### Для объектов

```c
static st_xxx_funcs_t xxx_funcs = {
    st_object_funcs,  // Наследуем функции от st_object_t
    .method1 = st_xxx_method1,
    .method2 = st_xxx_method2,
};
```

## Типы модулей

### Простой модуль (только контекст)
**Пример:** `src/modules/terminal/simple/`
- Модуль с контекстом, но без создания дополнительных объектов
- Все функции вызываются через контекст модуля

### Модуль с объектами
**Примеры:** `src/modules/ini/inih/`, `src/modules/monitor/xlib/`
- Модуль с контекстом + создает объекты (`st_ini_t`, `st_monitor_t` и т.д.)
- Контекст модуля управляет созданием и конфигурацией объектов
- Объекты имеют свои методы и владельца (контекст модуля)

**Примечание:** `monitor/xlib` и `ini/inih` по структуре схожи - оба создают объекты через контекст.
