# Best Practices и Edge Cases

Этот файл содержит дополнительные правила и edge cases, которые не вошли в основные технические гайды.

## Зависимости модулей

### POD-структуры vs вызовы методов

**Правило:** Использование типа из интерфейса другого модуля НЕ создает зависимость модуля.

**Создает зависимость:**
- Вызов методов через макросы типа `ST_XXXCTX_CALL()` или `ST_XXX_CALL()`
- Использование функциональной таблицы (vtable) модуля

**НЕ создает зависимость:**
- Использование POD-структуры из публичного интерфейса (например, `st_matrix3x3_t` в модуле `vec2`)
- Простое включение заголовочного файла для использования типов

**Пример (vec2 использует matrix3x3):**
```c
// include/steroids/modules/vec2.h
#include "steroids/modules/matrix3x3.h"

// Используем st_matrix3x3_t как POD-тип
void st_vec2_transform(st_vec2ctx_t *ctx, const st_matrix3x3_t *matrix, ...);
```

В этом случае зависимость от модуля `matrix3x3` в `mod_prereqs` **НЕ требуется**.

**Пример (drawq использует sprite):**
```c
// src/modules/drawq/simple/simple.c
// Вызываем методы sprite через макрос
ST_SPRITE_CALL(sprite, get_width);
```

В этом случае зависимость от модуля `sprite` в `mod_prereqs` **требуется**:
```c
static const st_modprerq_t mod_prereqs[] = {
    {"sprite", NULL},
    {0}
};
```

## POD структуры vs OOP объекты

### Когда использовать POD вместо наследования от st_object_t

**POD-структуры (не наследуются от st_object_t) используются для:**
- Performance-critical данных (матрицы, векторы, записи рендера)
- Данных, которые часто создаются на стеке
- Данных, которые копируются по значению
- Избежания overhead виртуальных таблиц

**Причины выбора POD:**
- Позволяет размещать данные на стеке без динамического выделения памяти
- Отсутствует overhead виртуальных таблиц и указателей на функции
- Копирование по значению более эффективно для небольших структур
- Важно для производительности в hot paths (например, рендеринг)

**Примеры POD-структур:**
- `st_matrix3x3_t` - матрица 3x3
- `st_drawrec_t` - запись для очереди рендера

**Паттерн использования POD:**
```c
// В интерфейсе - раскрытая структура
typedef struct {
    float r1c1, r1c2, r1c3;
    float r2c1, r2c2, r2c3;
    /*       0,    0,    1 */
} st_matrix3x3_t;

// Контекст модуля - наследуется от st_modctx_t
typedef struct {
    st_modctx_t;
    st_loggerctx_t *logger_ctx;
} st_matrix3x3ctx_t;

// Все операции над POD - через методы контекста
st_matrix3x3_t *(*identity)(st_matrix3x3ctx_t *ctx, st_matrix3x3_t *matrix);
```

**Наследование от st_object_t используется для:**
- Объектов с долгим lifecycle (окна, текстуры, спрайты)
- Объектов, требующих динамическое управление памятью
- Объектов, имеющих полиморфное поведение

**Причины выбора наследования от st_object_t:**
- Необходимо управление временем жизни через `destroy()`
- Объекты создаются редко и живут долго
- Размер объекта большой, и создание на стеке нецелесообразно
- Нужна полиморфность и виртуальные методы

**Важно:** Окончательное решение о выборе между POD и наследованием от `st_object_t` принимает пользователь, основываясь на требованиях конкретного модуля.

## Рабочий процесс AI-агента

### Проактивное выявление проблем

**Правило:** При работе с кодом следует проактивно выявлять потенциальные проблемы, но **не исправлять** их без явного разрешения пользователя.

**Что делать:**
1. Сообщить о найденных проблемах
2. Объяснить, почему это проблема
3. Предложить способ исправления
4. Дождаться подтверждения

**Чего НЕ делать:**
- Не исправлять проблемы в файлах, которые не были указаны для редактирования
- Не рефакторить код без запроса
- Не изменять логику работы программы

**Примеры проблем для упоминания:**
- Непроверенные return values критических функций
- Потенциальные NULL dereference
- Memory leaks
- Несоответствие сигнатур функций интерфейсу
- Missing const qualifiers

**Пример правильного поведения:**
```
Я заметил следующие потенциальные проблемы:

1. render.c:574 (примерно) - ST_GFXCTX_CALL(render_ctx->gfxctx, make_current) 
   не проверяет возвращаемое значение
   
2. render.c:604 (примерно) - Потенциальный NULL dereference gldebug_ctx

Хочешь, чтобы я их исправил, или ты сам это сделаешь?
```

**Примечание:** Номера строк в примерах указаны приблизительно и могут не соответствовать реальным номерам, так как код может измениться.

## Формат сообщений логирования

### Общий формат

```c
ST_LOGGERCTX_CALL(ctx->logger_ctx, уровень,
 "%s_%s: Сообщение с описанием действия/ошибки", st_module_subsystem, st_module_name);
```

**Уровни логирования:**
- `error` - ошибки, препятствующие работе
- `warning` - предупреждения о потенциальных проблемах
- `info` - информация о важных событиях
- `debug` - отладочная информация

### Содержание сообщений

**Для инициализации:**
```c
ST_LOGGERCTX_CALL(logger_ctx, info,
 "%s_%s: <Имя подсистемы> context initialized", st_module_subsystem, st_module_name);
```

Пример:
```c
ST_LOGGERCTX_CALL(logger_ctx, info,
 "%s_%s: Graphics context manager initialized", st_module_subsystem, st_module_name);
```

**Для деструкции:**
```c
ST_LOGGERCTX_CALL(ctx->logger_ctx, info,
 "%s_%s: <Имя подсистемы> context destroyed", st_module_subsystem, 
 st_module_name);
```

Пример:
```c
ST_LOGGERCTX_CALL(ctx->logger_ctx, info, "%s_%s: Render subsystem destroyed", 
 st_module_subsystem, st_module_name);
```

**Использование констант модуля:**
Константы `st_module_subsystem` и `st_module_name` используются **только если они объявлены** в текущей единице трансляции. Если они не объявлены, допустимо писать полное название модуля непосредственно в строке формата:

```c
// Если константы не объявлены
ST_LOGGERCTX_CALL(logger_ctx, info,
 "gfxctx_egl: Graphics context manager initialized");
```

**Для ошибок:**
```c
ST_LOGGERCTX_CALL(ctx->logger_ctx, error,
 "%s_%s: <Действие не удалось выполнить>: <краткое описание причины>", 
 st_module_subsystem, st_module_name);
```

**Примеры хороших сообщений об ошибках:**
- `"Unable to allocate memory for texture"` - конкретное действие + причина
- `"Failed to load image file: %s"` - действие + параметр
- `"Failed to make context current"` - конкретная операция

**Примеры плохих сообщений:**
- `"Error"` - слишком общее
- `"Failed"` - не указано что именно
- `"Something went wrong"` - бесполезное для отладки

### Сообщения с параметрами

Используй форматирование для включения важной информации:

```c
ST_LOGGERCTX_CALL(ctx->logger_ctx, error,
 "%s_%s: Failed to load texture from file: %s", st_module_subsystem, st_module_name, filename);

ST_LOGGERCTX_CALL(ctx->logger_ctx, warning,
 "%s_%s: Window size %dx%d exceeds maximum %dx%d", 
 st_module_subsystem, st_module_name, requested_width, requested_height, max_width, max_height);
```

**Правило:** Сообщение должно содержать достаточно информации для понимания:
- Что пошло не так
- При каких условиях это произошло
- Какие данные были вовлечены (если применимо)
